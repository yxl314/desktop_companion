# 竞品参考设计（逗逗游戏伙伴）

> 定位：从竞品逆向结果中提炼**可借鉴的代码设计与功能设计**，不照搬实现。
> 来源：Windows 客户端 v1.2.1.0 静态逆向。技术栈为 C#/WPF + WebView2 + Live2D + 腾讯 TRTC + SQLite；`rea` 结构化分析确认其非 Electron（browserWindows=0、preload=0、ipc=0），桥接走 WebView2 `hostObjects`。
> 边界：只借鉴设计；不复制其代码、美术素材与 Live2D 模型。逆向为静态分析，未见完整运行时行为。

---

## 一、架构对照

| 维度 | 逗逗 | 本项目 |
|---|---|---|
| 外壳 | C# / WPF（.NET 8） | C++ / Qt 6 + QML |
| 渲染 | Web 前端（Vite + Vue 3） | QML |
| 形象 | Live2D Cubism Web | v1 静态 PNG + 程序化动效，Live2D 后续可选 |
| 桥接 | WebView2 `hostObjects` + 方法注册表 | Bridge：`invoke` / `notify` |
| 语音 | TRTC 实时通道 + VAD/ASR/TTS | v1 不做 |
| 数据 | 服务端 + 本地 SQLite | 本地 SQLite + JSON |
| 部署 | 云端 SaaS、必须登录 | 本地优先、自带 API、可离线 |

结论：**它的“多窗口 + 桥接 + 本地壳”结构与我们同构**，参考价值集中在交互调度与数据分层；它的 SaaS 后端与 WebView 渲染不适用。

## 二、代码设计参考

### 2.1 双向桥接与方法注册表（值得参考）

它的做法：`INativeToWebBridge` / `IWebToNativeBridge` 两个方向分开；Web 调 C# 走 `WebMethodRegistry` + `WebRequestDispatcher`，按字符串方法名分派；C# 调 Web 走事件通道。

我们的做法：Bridge 已定 `invoke(action, payload)` 命令面 + `notify(event, payload)` 事件面（方案设计 §5.1/§5.10），新增能力注册到方法表。

### 2.2 窗口 id 体系与统一路由（值得参考）

它的做法：所有窗口用数字 id（`1000 main / 1001 model / 1002 im / 1003 chat / 1008 notification / 1011 shareAppScreen` 等），跨窗口消息统一 `sendMessage(targetId, type, data)`。

我们的做法：`WindowRegistry` 已承担同样职责（§5.10）；实现时建议沿用「id + 目标路由」写法，避免窗口之间直接互相持有对象。

### 2.3 组合根装配（值得参考）

它的做法：`AppContext` 与 `HostingExtensions` 负责装配，业务服务由容器构造，不相互 new。

我们的做法：§3.2 装配层已明确 AppContext 是组合根、业务服务不得相互 new。

### 2.4 透明窗口的兜底实现（值得参考其思路）

它的做法：为透明 WebView2 窗口写了两套实现（`StandardWpfTransparentWebWindow` / `HighPerformanceTransparentWebWindow`），说明这条路存在性能与合成问题，必须准备降级方案。

我们的做法：Qt 原生透明窗口问题少得多，但仍要准备「DWM 合成异常 / 全屏游戏抢层级」时的降级（关闭阴影、降低动效、重试置顶）。

### 2.5 稳定性组件（值得参考）

它的做法：`UIThreadHangCheckService`（UI 线程卡顿检测）、`ScreenSaverMonitor`、`SystemPowerMonitor`（休眠唤醒）、`CrossDayTimerService`（跨天）、`SingleFlight` / `SemaphoreLock`（并发抑制）。

我们的做法：对应为 UI 线程看门狗、电源/屏保事件、跨天计时、单飞请求保护。v1 至少做看门狗与单飞。

### 2.6 数据分层（值得参考）

它的做法：结构化数据进 SQLite（`LocalDatabase.db`、`GameScene.db`），配置与轻量状态用 JSON，敏感 token 走 `SecurityStorage`。

我们的做法：已定「JSON 存配置/角色/人设，SQLite 存聊天与记忆」（§5.7）；API Key 的本地存储与日志脱敏见 `G-H-11`、`G-H-12`。

### 2.7 事件总线（可选）

它的做法：`EventBus` 在进程内做模块解耦。

我们的做法：业务层已有信号槽，不建议再加一层全局事件总线，避免隐式依赖；跨窗口才用 Bridge 事件。

### 2.8 发布未裁剪 PDB（反例）

它的做法：随包发布了 `AIPetDesktop.*.pdb` 与 `DoudouAI.pdb`，源码文件名、类型名完全暴露。

我们的做法：发布包必须 strip 符号，调试包单独留存。

### 2.9 服务进程分离（暂不采用）

它的做法：`DoudouAIService.exe` 独立进程，与主壳走命名管道。

我们的做法：单进程足够；仅当语音/模型推理引入重依赖、需要崩溃隔离时再考虑，不在 v1 范围。

## 三、功能设计参考

### 3.1 核心（v1/v2 直接采纳）

| 设计 | 它的做法 | 我们的落点 |
|---|---|---|
| 动作优先级调度 | 动作带优先级抢占：说话 8~9 > 拖拽 6~7 > 点击 5 > 待机 1，配动作队列 | §5.6 Motion，`talk > drag > tap > idle` |
| 命中区分区 + 候选动作链 | 模型定义 `Face/Head/Body/leg/hl/hr/…` 命中区，点击按区找动作并降级（`TapFace → TapHead → Tap → Touch`） | 角色包 `meta.json` 的 `hitAreas[].actions` |
| 点击/拖拽阈值 | 8px 阈值区分点击与拖拽，拖拽三态动作 | §4.4、§5.2 |
| 贴边隐藏 + 悬浮球 | 拖到屏幕边缘收进边缘；可缩成小球常驻 | `PET-M-02`、`PET-M-03` |
| 鼠标穿透开关 | `setPetDesktopWindowMousePassthrough` 动态开关 | `PET-H-05`，实现见 §5.2 |
| 人设与记忆解耦 | 换人设只换 prompt，不动历史；新建人设才开新记忆空间 | `PSN-H-03`、§6.4 |
| 记忆 Event | 结构化条目，可 pin、可编辑、有上限、对话时按相关度调取 | `MEM-H-01~03`、§6.5 |
| 消息回溯 / 重启对话 | 回溯清除之后的消息与记忆；重启保留记录、重置记忆 | `CHAT-M-01/M-02`、`MEM-H-04` |
| 主动说话频率 | 空闲按频率主动发起，可关闭，可按场景限定 | `CHAT-M-03`、§6.6 |
| 打字机 + 自动播放语音 | 流式打字机；TTS 自动播放可关 | `CHAT-H-02`，TTS 留后续 |

### 3.2 加分（v2 再看）

| 设计 | 它的做法 | 我们的落点 |
|---|---|---|
| 好感度等级解锁 | 等级 2/5/15/20 解锁关系与奖励 | `INT-H-01`、`INT-M-01`、§8 |
| 卡片式回复 | 回复可带攻略/知识卡片，展开收起 | `CHAT-M-04` |
| 悬浮工具面板 | 鼠标悬停显示工具条，离开 500ms 隐藏 | 待定，可按需加 |
| 右键长按 1.2s | 触发特殊互动，区分普通右键 | 可作彩蛋，不占需求 |

| 隐私 PIN 锁 | 聊天记录加密，查看需密码 | 隐私模式，后续 |

### 3.3 后续评估（不在 v1）

- 屏幕感知：它用进程 + 前台窗口 + 截图 + VLM；我们 v2 先做进程/窗口标题的轻量感知，截图与多模态默认关闭、按需开启。
- VLM 回放：把识别过程（画面分析 → 推理 → 搜索 → 回复）可视化回放，交互参考价值高，但依赖多模态模型，后续再说。
- 实时语音：它走 TRTC；我们先做「按住说话 + 流式 TTS」，不接 RTC。

### 3.4 不参考

云端账号与云同步、会员墙与商城、道具/任务/签到/抽卡、RTC 通话计费、OEM 渠道定制、直播模式、3D 旋转录制——这些与本项目「本地优先、开源、自带模型」的定位冲突。

## 五、实现提醒

1. **动作系统先定优先级表再产出素材**：优先级是调度骨架，素材后补只需填表；反过来做必然返工。
2. **透明窗口一开始就带降级开关**：全屏游戏抢层级、DWM 合成异常时能退化成普通窗口，而不是直接不可用。
3. **Key 与日志脱敏从第一天做**：事后补要翻遍所有日志点，成本高（对应 `G-H-11`、`G-H-12`）。
